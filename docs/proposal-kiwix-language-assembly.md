# Proposal: Kiwix composes a map's language versions on download

Status: proposal for the Kiwix product lead and the openZIM developers,
2026-10-23. Nothing in Kiwix depends on it yet. Numbers marked *estimate*
are not measured; the others are measured on StreetZim's published maps.

## Summary

1. **Problem.** A StreetZim map in many languages is many full ZIMs of
   nearly the same bytes: Switzerland's 23 language versions are 70.4 GB
   as separate files.
2. **Proposal.** Publish one multilingual base per region, small packs per
   language and a recipe per version; the Kiwix app downloads the parts it
   lacks and composes the version on the device. The result is an ordinary
   ZIM, byte for byte the file StreetZim tested.
3. **Numbers.** The parts take 7 to 10 times less mirror space than the
   files (Switzerland about 8.5 GB instead of 70.4 GB). A user who has the
   base downloads 0.77-0.86 GB for another Swiss language instead of
   3.03-3.12 GB.
4. **The ask.** Does Kiwix want per-language versions beyond the
   multilingual base, and if so, which of the four options below?
5. **Who builds what.** StreetZim: the format spec, test files, a C++
   splicer for libkiwix and the Zimfarm side. Kiwix: the catalog entries
   and the download step in each app, about 12-23 developer-weeks in all
   (*estimate*).

## Why

Zimfarm can already build the multilingual base (`streetzim
--multilingual`, [zimfarm.md](zimfarm.md#multilingual-maps---multilingual)):
map labels in 21 languages plus the region's own, search by those names,
and the viewer's interface in 23 languages. Hosting only that base is the
simplest choice. What the base cannot hold for every language at once is
the Wikipedia articles in the visitor's language and Kiwix's own search
in it (a ZIM has one title index and one full-text index). A language
version adds those.

Storing every language version as its own file costs this (measured on
the versions published on StreetZim's builder page):

| region | versions | each version | all versions as files | as parts (base + packs) | files / parts |
|---|---|---|---|---|---|
| Switzerland | 23 | 3.03-3.12 GB | 70.4 GB | 8.5 GB | 8.3 |
| Baltics | 22 | 1.27-1.32 GB | 28.2 GB | 4.2 GB | 6.8 |
| Greece | 22 | 1.16-1.21 GB | 25.8 GB | 2.6 GB | 10.0 |
| Iceland | 19 | 0.35-0.36 GB | 6.7 GB | 0.8 GB | 8.4 |

Half to two thirds of the parts are search packs: each version's search
pack indexes all of the base's pages again, in that version's language
(Switzerland: 0.21 GB each).

## How it works

A language version is made of:

- the region's **base** ZIM (2.28 GB for Switzerland);
- **Wikipedia packs**: small ZIMs with the region's articles in one
  language (the region's own languages and the version's);
- a **search pack**: libzim's title and full-text indexes over the base and
  those packs, stemmed in the version's language;
- a **recipe** (JSON, 14-16 MB for Switzerland, 3.7 MB gzipped): the
  version's bytes in order.

```
language version (Swiss German, 3.03 GB)
┌──────────┬─────────────────────────────┬─────────────────────┬──────────────┬─────┐
│ new head │ base: clusters and entries, │ packs' clusters     │ new tables   │ MD5 │
│  64 KiB  │ at their original offsets   │ (de fr it rm search)│ (~9 MB)      │     │
└──────────┴─────────────────────────────┴─────────────────────┴──────────────┴─────┘
  inline          from the base file           from the pack files     inline
```

The recipe lists those pieces: ranges of the base and of each pack, and
the few MB of generated bytes inline. It carries a SHA-256 for every
16 MiB of every input and the MD5 of the result, so every byte is checked
before it is written, and a deterministic UUID derived from the inputs, so
a rebuilt part gives a new book. StreetZim's merger
(`tools/langpack/merge_zim.py`) and recipe writer
(`tools/langpack/recipe2.py`) produce the same byte stream, and every
published version passed zimcheck, libzim's own check, kiwix-serve
`/suggest` and `/search`, and the viewer in a browser.

This runs today on StreetZim's website: the builder page composes a
version in the browser (Swiss versions in 10-13 minutes, everything
downloaded from archive.org), a relay streams versions as files, and each
version has a torrent.

**In Kiwix** (the proposed option) the flow would be:

1. The catalog lists each version as a book (its own UUID, Name, Title and
   Language) with a link to its recipe. That link must not use the
   `http://opds-spec.org/acquisition/open-access` relation: every released
   libkiwix, up to 14.2.1, takes each such link as the book's download,
   whatever its type, and keeps the last one. A generic
   `http://opds-spec.org/acquisition` link without a length fits, to be
   tested with each app.
2. The app downloads the parts it does not have (base, packs) as ordinary
   files, each with its `.meta4`: the catalog carries no checksums, so
   they come from there, as for any ZIM, and the recipe comes from the same
   origin over HTTPS.
3. It splices the parts as the recipe says, checks every chunk and the
   final MD5, and adds the result to the library.

Kiwix Desktop downloads through libkiwix's aria2-based downloader; Kiwix
Android and Kiwix iOS have their own. libkiwix would give all three the
recipe reader and the splicer, through java-libkiwix and the iOS bridge,
and each app keeps its own downloads.

**Older apps** see a version only through a plain download link, which
needs someone to serve each version as a whole file: a relay run by Kiwix,
or prebuilt files for the languages that matter most. StreetZim's own
relay is not enough: it refuses a whole-file request for a large version
(its free plan allows 50 subrequests per request), and the mobile apps do
not download torrents.

## Options compared

Switzerland, 23 languages.

| | stored on the mirrors | download for one version | download for another language | app changes | who runs what |
|---|---|---|---|---|---|
| Base only (no per-language versions) | 2.3 GB | 2.3 GB | none | none | nothing new |
| Prebuilt files | 70.4 GB | 3.0-3.1 GB | 3.0-3.1 GB | none | Zimfarm builds 23 files per region |
| **Compose on download** (proposed) | 8.5 GB | 3.1 GB (base + packs) | 0.8-0.9 GB | the download step in each app, via libkiwix | Zimfarm builds the parts |
| **Relay** | 8.5 GB, and every download passes through the relay | 3.0-3.1 GB | 3.0-3.1 GB | none | Kiwix runs a relay that serves each version as a file |
| **Viewer switch**: one ZIM with every language | about 3.9 GB (*estimate*) | about 3.9 GB | none | none | Zimfarm builds one bigger file |
| **Recipe as a book**: libzim reads the recipe | 8.5 GB | 3.1 GB | 0.8-0.9 GB, no full copy | libzim's file layer, the library, every app | Zimfarm builds the parts |

- **Compose on download** saves mirror space and lets a user with the
  base add a language cheaply. The device still stores a full-size file
  per version. Older apps need the relay or prebuilt files.
- **Relay** needs no app change and serves older apps, but every byte goes
  through a server Kiwix runs instead of the mirrors, and nothing a device
  has is reused. It combines well with Compose on download.
- **Viewer switch** needs nothing new in Kiwix: the viewer already shows
  labels, search names and the interface in the visitor's language. Every
  download carries every language's Wikipedia (about 25% more than one
  version for Switzerland, more for regions with larger Wikipedias), and one
  search index serves all languages with one stemmer.
- **Recipe as a book** extends what libzim does for split ZIMs (one archive
  from several files) to ranges of files: nothing is copied, and one base on
  the device serves every language. It changes libzim's I/O core, the parts
  must stay on the device, and a version opens only in apps with the new
  libzim.

## What StreetZim offers, what Kiwix would build

All durations are *estimates*.

| work | who | weeks |
|---|---|---|
| Format spec, schema, test files (a small base, packs, recipes, expected results) | StreetZim | 1-2 |
| libkiwix: recipe reader, checks, splicer with resume; StreetZim offers the C++ code | StreetZim, reviewed by libkiwix maintainers | 2-4 |
| Zimfarm: an offliner for the packs and recipes; uploading recipes | StreetZim, with Zimfarm maintainers | 2-3 |
| Catalog: the recipe link, the book fields, `.meta4` for the parts, packs kept off the list | Kiwix / openZIM | 1-2 |
| Kiwix Desktop, Android, iOS: a language choice on a map, the download and splice step | Kiwix | 2-4 each |
| **Total** | | **12-23** |

StreetZim keeps building and checking the bases, packs and recipes for
every region it publishes.

## Open questions

1. Per-language versions at all, or the multilingual base only?
2. Which option, or Compose on download plus a relay for older apps?
3. Whose format: StreetZim's, or an openZIM one ("a ZIM as ranges of other
   ZIMs") that other scrapers could use for their own language variants?
4. Packs in the catalog: hidden, or shown as add-ons of the base?
5. For older apps: a Kiwix relay, prebuilt files for the top languages, or
   nothing?
6. Recipe size: binary inline bytes beside the JSON would remove most of
   today's 14-16 MB.

## Details

- **Spec and design.** [language-packs.md](language-packs.md) (the
  design); the recipe format is in `tools/langpack/recipe2.py`, the merger
  in `tools/langpack/merge_zim.py`, the browser's splicer in
  `web/build/assembler-worker.js`, the relay in `build-proxy/`.
- **Measurements.** Sizes from the versions published on the builder
  page's preview for Switzerland (2026-10-22 base), the Baltics, Greece and
  Iceland (2026-10-23). Each version now gets a search pack in its own
  language; before 2026-10-23, versions with the same packs shared one
  stemmed in English, and Switzerland's parts were 7.66 GB (the 4 extra
  search packs add 0.84 GB). Browser times: de and ja 10 min, it 10.5, fr
  12, ar 13 (rm took 26 while the host's disk was saturated).
- **Version names.** Each version's Name is `osm_<lang>_<region>`, so a
  multilingual base built on Zimfarm should be `osm_mul_<region>`; the
  Flavour should stay stable across rebuilds.
- **Known gaps.** Hindi labels do not render yet (no Devanagari glyphs in
  the viewer). A version carries some base bytes nothing uses any more
  (the base's old indexes: about 3.6% of a Swiss version). Continents are
  out of scope for now: a version may need at most 2 GiB of packs.
- **Updates.** A new base or pack means new recipes and new UUIDs; the
  parts on the mirrors are never changed in place, so a new viewer means a
  new base file.
