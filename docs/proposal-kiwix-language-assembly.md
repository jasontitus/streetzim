# Proposal: Kiwix composes a map's language versions on download

Status: proposal, 2026-10-23, revised after review, for the Kiwix product
lead and the openZIM developers. Nothing in Kiwix, libkiwix or Zimfarm
depends on it yet. Numbers marked *estimate* have not been measured. GB
means 10^9 bytes; recipe chunks are 16 MiB (2^24 bytes).

## Summary

1. **Problem.** A StreetZim map offered in many languages is many full
   ZIMs of nearly the same bytes: Switzerland's 23 language versions are
   70.4 GB as separate files.
2. **Proposal.** Publish one multilingual base per region, small
   per-language packs and a recipe per version; a Kiwix app downloads the
   parts it lacks and composes the version on the device.
3. **Numbers.** The parts take 7 to 10 times less mirror space than the
   files (Switzerland 7.66 against 70.4 GB). A user who has the base
   downloads 0.77-0.86 GB for another Swiss version instead of
   3.03-3.12 GB.
4. **The decision asked.** Whether Kiwix wants per-language versions beyond
   the multilingual base (the [baseline](#baseline-host-the-multilingual-base-only)),
   and if so which of four options: **Compose on download** (proposed),
   **Relay**, **Viewer switch** or **Recipe as a book**.
5. **Who builds what.** StreetZim: the format spec, test vectors, a C++
   splicer for libkiwix and the Zimfarm offliner. Kiwix: the catalog, and
   the download and composition step in each app (*estimate*: 12-23
   developer-weeks in all, [Effort](#effort)).

## Baseline: host the multilingual base only

Zimfarm can build the multilingual base now (`streetzim --multilingual`,
[zimfarm.md, "Multilingual maps"](zimfarm.md#multilingual-maps---multilingual)).
It is one ZIM per region with:

- map labels in 21 languages plus the region's own (`name:XX` in the
  tiles), except that Hindi labels do not render yet: the viewer has no
  Devanagari glyphs;
- search by the names in those languages;
- the interface in those 21 languages, English and Swedish (Romansh falls
  back to German).

What it lacks per language is the Wikipedia articles in the visitor's
language and Kiwix's own search (libzim's title and full-text indexes) in
it. Hosting the base alone costs nothing new in Kiwix. Every option below
adds those two things, at the costs given.

## What a language version is

StreetZim makes language versions today without storing them. A version
is:

- the region's **base** ZIM (which already carries English Wikipedia);
- **Wikipedia packs**: small ZIMs with the region's articles in one
  language; every version carries the packs of the region's own languages
  and of its own language;
- a **search pack**: a ZIM holding only libzim's title and full-text
  indexes over the base's pages and those packs' articles;
- a **recipe** (`streetzim-recipe/2`, JSON): the version's bytes in order,
  as ranges of the base and the packs plus a few MB of generated bytes,
  with SHA-256 hashes to check every input and the MD5 of the result
  ([below](#the-recipe)).

Splicing the ranges gives a normal ZIM, byte for byte the file StreetZim
merged and checked before publishing the recipe (zimcheck, libzim's own
check, kiwix-serve `/suggest` and `/search`, the viewer in a browser).
`tools/langpack/merge_zim.py` (the merger) and `tools/langpack/recipe2.py`
(recipes) emit from one byte stream, so the two cannot disagree. Three
consumers exist: the website's builder page splices in the browser
(`web/build/assembler-worker.js`), a relay streams versions as files
(`build-proxy/`, [its README](../build-proxy/README.md)), and each version
has a torrent.

### The published data

The numbers here come from four regions published on a preview of the
builder page,
<https://streetzim--swiss-languages-tazg4jsx.web.app/build/> (a preview
channel, which expires), with packs in archive.org items, Switzerland's in
a test item. The Swiss entries there were made from the 2026-10-22 base;
the Swiss map was rebuilt on 2026-10-23 and archive.org now holds only the
new base, so those entries build only from a local copy of the old one
until new recipes are published ([Updates](#updates) is about exactly
this).

File sizes (the parts count each Wikipedia pack and each search pack file
once):

| region | base | versions | each version | all versions as files | parts: base + Wikipedia packs + search packs | files / parts | search packs' share of the parts |
|---|---|---|---|---|---|---|---|
| Switzerland | 2.28 GB | 23 | 3.03-3.12 GB | 70.4 GB | 7.66 GB = 2.28 + 1.27 + 4.11 | 9.2 | 54% |
| Baltics | 0.98 GB | 22 | 1.27-1.32 GB | 28.2 GB | 4.15 GB = 0.98 + 0.39 + 2.77 | 6.8 | 67% |
| Greece | 1.05 GB | 22 | 1.16-1.21 GB | 25.8 GB | 2.53 GB = 1.05 + 0.25 + 1.23 | 10.2 | 48% |
| Iceland | 0.33 GB | 19 | 0.35-0.36 GB | 6.7 GB | 0.80 GB = 0.33 + 0.03 + 0.44 | 8.4 | 55% |

- **Search packs are most of the parts.** A search pack indexes every page
  of the base again, so it grows with the base: Switzerland's are about
  0.21 GB each, against 1.27 GB for all 22 Wikipedia packs together.
- **Versions with the same packs share one search pack, stemmed in the
  base's language** (English for these bases): Switzerland's de, en, fr,
  it and rm versions (all five carry exactly the de, fr, it and rm packs)
  share one, Greece's el and en another. A search pack per version, each
  stemmed in its own language, would add 4 × 0.21 = 0.84 GB to
  Switzerland's parts (+11%) and 57 MB to Greece's.
- **A version downloads its packs whole or in ranges.** Swiss German needs
  0.77 GB of pack files (de, fr, it, rm, search) or 0.74 GB of the ranges
  its recipe reads, rounded to 16 MiB chunks; all Swiss versions need
  0.77-0.86 GB of files.
- **Every version keeps base bytes nothing references any more**: the
  base's own Xapian indexes, title listing and pointer lists (replaced by
  the search pack's and by generated ones) and its old metadata and
  `map-config.json`. On the current (2026-10-23) Swiss base that is about
  109 MB (old Xapian 102 MB, pointer lists 6 MB, listing 1.5 MB), 3.6% of
  a version; on Greece's, 32 MB, 2.7%.
- **Which languages are published.** Each region's menu is the 21 label
  languages, English and the region's own languages that have a Kiwix
  Wikipedia ZIM (`CORE_LANGS` in `tools/langpack/region_meta.py`); a
  version is published only when every check passes. On the preview,
  Baltic lt, lv and et failed the interface check (the viewer has no
  interface in those languages), and Iceland's en, tr and vi failed the
  Kiwix search check (is failed both); those versions are missing.
- **Continents are out of scope.** A version may need at most 2 GiB of
  packs and a base at most 8 GB; a continent's search packs alone pass
  that (Europe's would be about 2.8 GB).
- **Times, measured on StreetZim's build host.** Making Switzerland's
  packs, search packs, recipes and checks took 405 min on 2026-10-22
  (search packs 1 h 58 min, checks 3 h 45 min). The builder page in
  headless Chromium, everything downloaded from archive.org through the
  range proxy, composed Swiss versions in 10 min (de, ja), 10.5 (it), 12
  (fr), 13 (ar) and 26 (rm, while the host's disk was saturated).

### The recipe

The fields that matter here (a Swiss German recipe; `…` marks values cut
short; also present and left out: `merger`, `file_name`, `map_language`,
`fingerprint`, `generated_sha256`, `base.slots`, each pack's `uuid` and
`articles`):

```json
{"format": "streetzim-recipe/2", "uuid": "f8faf231-92e1-51f2-bd45-d9cd8afb2688",
 "name": "osm_de_switzerland", "title": "Schweiz", "language": "deu",
 "flavour": "maxi_wiki-en-de-fr-it-rm",
 "size": 3025954350, "md5": "<the ZIM's own checksum>", "file_md5": "<md5sum of the file>",
 "base": {"file": "osm-switzerland-2026-10-22.zim", "size": 2283524130, "uuid": "c6304e7e…",
          "range": [65616, 2283524114], "chunk": 16777216, "sha256": ["…137 hashes…"],
          "mask": [[777355760, 1048576], "…"]},
 "packs": {"de": {"file": "osm_switzerland_wiki-de_2026-10-22_c6304e7e.zim",
                  "url": "{proxy}/<archive.org item>/<file>", "size": 229454627,
                  "chunk": 16777216, "sha256": ["…"]},
           "fr": "…", "it": "…", "rm": "…",
           "search": {"kind": "search", "file": "osm_switzerland_search-de-fr-it-rm_…", "…": "…"}},
 "segments": [{"src": "inline", "len": 65616, "data": "<base64>", "sha256": "…"},
              {"src": "base", "off": 65616, "len": 777290144},
              {"src": "pack", "pack": "de", "off": 65616, "len": 225997506},
              "…",
              {"src": "md5"}]}
```

- **Segments.** The version is the segments in order: `inline` bytes
  (base64, each with its own SHA-256), ranges of the base or of a pack,
  and the 16-byte MD5. The Swiss German recipe (and the en, fr, it and rm
  ones, which carry the same packs) has 1,997 segments. Eight ranges of
  1 MiB or more carry 99.6% of the bytes: the base on either side of its
  viewer files, the clusters of the four Wikipedia packs and of the search
  pack, and one 4 MB run of the base's tables. The rest is the generated
  head (header and MIME list, 64 KiB), the viewer files (1.4 MB, below)
  and the generated tables at the end (pointer lists, the title listing,
  the packs' directory entries), interleaved with short base ranges.
- **Layout.** The base's clusters and directory entries stay at their own
  offsets, so a version starts with the base's bytes. Pack paths
  (`~w/<lang>/…`) sort after every base path; a pack only adds entries.
  `map-config.json` and the metadata (Name, Title, Language, Flavour,
  Description) are generated.
- **Checks.** Every input is hashed in 16 MiB chunks from offset 0 (the
  base with its `mask` ranges zeroed). Inline bytes carry their own
  SHA-256. The result's MD5 (the checksum libzim verifies) and `file_md5`
  are compared at the end.
- **UUID.** `derive_uuid` in `merge_zim.py`: a UUIDv5 of the base UUID,
  the pack UUIDs, the language, the merger version, a hash of the
  generated `map-config.json` and metadata, and the inputs' MD5s. The same
  inputs give the same UUID; any change gives a new one, which Kiwix needs,
  since it dedupes books by UUID.
- **Viewer slots and the mask.** StreetZim's own copies of a base can have
  their viewer patched in place, in fixed-size slots
  (`cloud/patch_viewer_inplace.py`), keeping size and UUID. The recipe
  carries the slots inline, and `base.mask` lists them and the base's
  checksum; the base's chunk hashes are taken with those bytes zeroed.
- **Size.** Switzerland's recipes are 13.7-15.5 MB of JSON (German 3.7 MB
  gzipped), almost all of it the base64 inline bytes (10.1 MB raw);
  Greece's 4.8-5.8 MB, Iceland's 2.2-2.3 MB. They grow with the packs'
  entries, not with the base.

**What the format needs before Kiwix uses it** (StreetZim's side of the
spec):

- *Names.* Each version's Name is `osm_<lang>_<region>`, so a base built
  on Zimfarm must not be named `osm_en_<region>` (the English version's
  Name); `osm_mul_<region>` fits. The Flavour today lists the packs
  (`maxi_wiki-en-de-fr-it-rm`) and would change whenever a region language
  is added; it should be stable, with the pack list in Tags or the
  Description.
- *Download URLs.* Pack URLs are a template for StreetZim's range proxy
  (`{proxy}/…`) and the base has none in the recipe. Each input needs a
  real URL with a `.meta4` (mirrors and checksums), like any ZIM.
- *Catalog fields.* A version that exists only as a recipe still needs
  every field a libkiwix `Book` has (article and media counts, tags,
  creator, publisher, date, illustration): in the recipe, or produced by a
  catalog generator that reads the base and the recipe.
- *Hashes.* For Kiwix the mask can be empty (mirrors never patch files in
  place), plus a hash of the whole unmasked base so an app can check a
  local base in one pass. Masking the header's UUID as well would let an
  older base with the same content serve ([Updates](#updates)).

## Option 1: Compose on download (proposed)

### Catalog

A version is an OPDS entry with its own UUID, Name, Title and Language in
that language, size and illustration, plus a link to its recipe.

- **The recipe link must not use the `open-access` acquisition relation.**
  Every released libkiwix, up to 14.2.1 (May 2026), reads every
  `rel="http://opds-spec.org/acquisition/open-access"` link whatever its
  type and keeps the last one's URL and length, so an older app would try
  to download the recipe as the ZIM (libkiwix's main branch now skips
  unknown types). The recipe link should use another relation, for example
  the generic `http://opds-spec.org/acquisition`, carry no `length`, and be
  tested against each app's OPDS parser.
- **Checksums are not in the catalog.** A `Book` carries no checksum; the
  apps get them from the `.meta4` file over HTTPS. Recipes should come
  from the same trusted origin over HTTPS, or, if mirrored, the catalog
  entry should carry the recipe's SHA-256.
- **Packs and search packs** are ZIMs but useless alone (their articles
  link back into the base); they should stay off the catalog while on the
  mirrors.
- **A plain link for older apps** (an ordinary `open-access` link to a
  ZIM) exists only if someone serves each version as a whole file: a relay
  that streams whole files ([Relay](#option-2-relay)) run by Kiwix, or
  prebuilt files for the versions older apps should get. StreetZim's own
  relay does not qualify: a whole-file GET of a large version is refused
  (the free plan's 50 subrequests per request), mobile apps do not
  download torrents, and the Swiss entries carry no webseed.

### Download and composition

Kiwix Desktop downloads through libkiwix's aria2-based downloader; Kiwix
Android and Kiwix iOS have their own download code. libkiwix would give
all three the recipe reader, the base lookup and the splicer (through
java-libkiwix and the iOS bridge); each app keeps its own downloads. The
simplest flow downloads whole files:

1. Fetch the recipe and check it ([Integrity](#security-and-integrity)).
2. Look for the base in the library by `base.uuid` and check it against
   the base's hashes (one read of the base).
3. Download what is missing, the base and the packs, as ordinary files
   with their `.meta4`.
4. Splice the segments into the output in order, checking every chunk and
   inline piece, computing the MD5 as the bytes go out, and compare it with
   `md5` and `file_md5`. Memory stays constant (a chunk at a time).
5. Add the result to the library; delete the packs; keep or delete the
   base as the user chooses.

Whole files suit today's downloaders: aria2 and the mobile downloaders
write one file per download, and none writes ranges of several files into
one output. Their cost: a download that does not check the file's own
`.meta4` hash shows a bad mirror copy only at step 4, and that costs the
whole file. Fetching ranges instead (as the builder page does) costs one
chunk per bad copy and saves the packs' temporary copy, but needs a new
fetcher in each app, and a range can be checked only once every 16 MiB
chunk it touches has arrived.

The splicer is small: `web/build/assembler-worker.js` (about 500 lines of
JavaScript, plus `fetcher.js` for ranges) and `recipe2.py materialize`
hold the whole algorithm. A C++ version: *estimate*, 300-500 lines plus
tests.

### Resume

Input downloads resume as they do today. The splice restarts at the last
chunk boundary written: the MD5 of the part already written is computed
again at disk speed (Switzerland's 3 GB: about 4 s at the 0.8 GB/s the
merger measured on the build host), or its state is saved, as the
browser's WASM MD5 (hash-wasm) allows.

### Storage

- **On the device, nothing is saved.** The version is a full-size file
  (3.03-3.12 GB for Switzerland), plus the base if the user keeps it.
- **Peak during composition:** base + packs + output, Switzerland 2.28 +
  0.77 + 3.03 = about 6.1 GB.
- **In place.** Apart from the head (64 KiB) and the viewer slots
  (1.4 MB), a version's first 2.28 GB are the base's bytes at the same
  offsets, so an app that does not keep the base could turn the base file
  into the version (rewrite those bytes, truncate at `base.range[1]`,
  append the rest): peak 3.8 GB. Not where the app may not write the file:
  Android's Storage Access Framework folders, files opened in place on
  iOS. On copy-on-write filesystems (APFS, btrfs) a clone keeps both files
  for little more than one. *Not implemented anywhere.*

### Updates

- **Any new input means new recipes and new UUIDs.** A rebuilt base or
  pack changes the inputs' UUIDs or MD5s and so every affected version's
  UUID. With stable Names and Flavours, the apps' update check (same Name
  and Flavour, newer date) can offer the new version; this needs testing
  in each app.
- **After step 5 the packs are gone,** so a rebuilt pack means downloading
  every pack of the version again, and the base too if it was deleted.
- **Files on mirrors are immutable.** A new viewer is a new base file with
  a new UUID, so every recipe changes. The old base on the device differs
  from the new one in the viewer slots, the checksum and the header
  (which holds the UUID): it fails chunk 0 unless the recipe masks the
  header too (an open question). StreetZim has stopped patching published
  bases in place once their recipes are out for the same reason (such
  uploads are refused).
- **Inputs must stay published while recipes name them.** The Swiss
  preview above shows what happens otherwise.

### Older apps

They see only what the catalog gives them as a plain link. Without a
whole-file relay or prebuilt files, a version is not offered to them.

## Option 2: Relay

A server streams each version as an ordinary ZIM file, splicing the parts
on the fly. Kiwix would run it; StreetZim's relay (`build-proxy/`, a
Cloudflare Worker reading archive.org) shows it works.

- **For.** No change in the apps: the catalog gives a URL and a `.meta4`
  for it (the MD5 is known from the recipe in advance; the relay is the
  `.meta4`'s only mirror). Older apps get every version. The parts on the
  mirrors are the same as option 1's, and so is the storage saving.
- **Against.** Every byte of every version download passes through the
  relay, bypassing the mirror network; that traffic is the real cost. A
  user downloads the whole version every time, base included, and a
  device with the base gains nothing. StreetZim's instance runs on
  Cloudflare's free plan (100,000 requests a day per account, 50
  subrequests per request, so it serves only ranges of a large version);
  those limits are StreetZim's choice, not the design's.

## Option 3: Viewer switch

One ZIM per region carries every language: the base, every Wikipedia pack
and one combined search index. The viewer already shows labels, search
names and the interface in the visitor's language.

- **For.** No composition, no recipes, no catalog change, nothing new in
  the apps; one file per region on the mirrors, about half of option 1's
  parts (*estimate*: Switzerland 2.28 + 1.27 + about 0.3 for a combined
  index = 3.9 GB, against 7.66 GB). A device holds every language at
  once.
- **Against.** Every download carries every language's Wikipedia: about
  25% more than one version for Switzerland (3.9 against 3.03-3.12 GB,
  *estimate*); regions with larger Wikipedias grow faster. One title
  index and one full-text index serve every language with one stemmer;
  option 1 already does that for five of the 23 Swiss versions (above).
  The ZIM's `Language` metadata can list several codes; how kiwix-serve's
  multi-book `/search`, which refuses books in different languages,
  treats a book with several is to be checked.

## Option 4: Recipe as a book

libzim opens a recipe directly, the way it opens a split ZIM
(`file.zimaa`, `file.zimab`, …) as one archive: its `FileCompound`
generalised from whole files to (file, offset, length) parts, plus the
inline bytes from a sidecar. Nothing is spliced or copied.

- **For.** One base on the device serves every version; each extra
  version costs its packs (0.77-0.86 GB for Switzerland) and no full copy.
  kiwix-serve could serve versions the same way.
- **Against.** A change in libzim's I/O core. Switzerland's recipes have
  about 2,000 parts (*estimate*: about 10 if the base's tables were
  inlined in the sidecar). The inputs must stay on the device: deleting
  the base breaks every version. The library needs a book whose path is a
  recipe, and every app must ship the new libzim before it can open one.

## Security and integrity

- **The recipe is the trust anchor.** Whoever writes it decides the
  bytes, inline viewer code included, as whoever publishes a ZIM decides
  its contents. It must come from the catalog's origin over HTTPS, or carry
  a SHA-256 in the catalog entry when mirrored. Signing recipes or
  catalogs is open.
- **Every output byte is checked.** Base and pack ranges against their
  chunk's SHA-256, inline bytes against their own SHA-256; the last 16
  bytes are the MD5 the app computes, compared with the recipe's. The app
  also checks that the result's header UUID is the catalog entry's id.
- **Mirrors are untrusted.** A bad copy makes a download fail, never
  changes it.
- **Parsing.** Refuse an unknown format, a recipe over a size limit (the
  builder page's is 32 MiB), a chunk list whose length does not match the
  input's size, a segment outside its input, lengths that do not add up to
  `size`, and an input file name with a path in it. Output paths are the
  app's, never the recipe's.
- **Resources.** Constant memory; free disk checked before starting.
- **Privacy.** The apps fetch the same kinds of files from the same
  mirrors as today; no new server learns which version a user composes
  (a relay does, in option 2).

## Prior art

- libzim's split ZIMs (`.zimaa`, `.zimab`, …): one archive from several
  files, the starting point of option 4.
- zim-tools once shipped `zimdiff` and `zimpatch`: a diff ZIM between two
  versions of a book, applied to the older one. A recipe is the reverse: it
  adds to a base instead of replacing it, and needs no ZIM logic to apply.

## Open questions

1. **Who owns the format?** StreetZim's alone, or an openZIM one ("a ZIM
   as ranges of other ZIMs") other scrapers could use for their own
   per-language variants.
2. **Recipe size.** 13.7-15.5 MB of JSON for Switzerland (3.7 MB gzipped
   for German). Binary inline bytes beside the JSON would remove the base64
   overhead; the viewer slots are the same in every version of a region.
3. **Search packs.** Whether each version gets its own stemmer (+11% for
   Switzerland) or versions share, and whether Kiwix's search should rather
   learn to use several indexes.
4. **Packs in the catalog:** hidden, or add-ons of the base?
5. **The base after composition:** keep both files, transform in place, or
   clone on copy-on-write filesystems; and what the library shows.
6. **Whole files or ranges** for the first libkiwix version.
7. **The plain link:** a Kiwix relay, prebuilt files for some versions, or
   none.
