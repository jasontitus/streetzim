# Viewer UI language

The map viewer (`index.html`) and the Find page (`places.html`) show their
buttons, panels, messages, Find chips, turn-by-turn instructions and place
sheet in the map's language: map-config.json `language`, which
`--language` sets ([languages.md](languages.md)). A map built with
`--language de` gets a German viewer. A language without a table (today:
everything but German) shows English, and an English build is unchanged,
character for character.

Not translated, by design: place names, addresses, Wikipedia and Wikidata
text and other data (they are in the map's language already); licence
texts and product names in About (`translate="no"`); MapLibre's
"© OpenStreetMap contributors" attribution; technical details on the error
pages (user agent, URLs, the debug log); coordinates (always `47.37690,
8.54170`). Text the *build* writes is English in every build for now — the
Kiwix search pages, the article back bar and footer, a ZIM's default title
and description (part B2 of the bilingual design).

## How it works

- **English lives at the call site**: `szT('routing.no_route', 'No route
  found')`, `szT('find.none_in_map', 'No {chip} in this map', { chip: … })`,
  and for counts `szTn('place.links', n, { one: '{n} link', other: '{n}
  links' })`. Whole phrases with `{placeholders}`, never fragments glued
  together, because word order differs between languages. Keys are dotted
  lower-case. (`szT`, not `t`: the viewer has many local variables named
  `t`, and a shadowed `t()` would fail only at run time.)
- **Static markup** carries `data-i18n="key"` (its text),
  `data-i18n-title`, `data-i18n-placeholder`, `data-i18n-aria-label`. Text
  that code fills in is marked `data-i18n-code`; text that stays as written
  `translate="no"`.
- **The tables are inlined.** A published ZIM can never gain a file and an
  in-place viewer patch rewrites only the slots
  ([viewer-slots.md](viewer-slots.md)), so there is no i18n.json:
  `tools/build_i18n.py` writes the runtime and each page's own keys into
  part `005-i18n.html` and between the `SZ-I18N` markers in places.html.
  An existing German ZIM gets its German UI from an ordinary
  `patch_viewer_inplace.py`.
- **Chosen once map-config.json has loaded**: `szUseLanguage(config.language,
  location.search)` picks the table, translates the static markup in one
  pass, sets `<html lang>`, and fires `sz-ui-language` for code that
  rendered text earlier (the online-preview banner). What shows before that
  — "Loading places index…", an unsupported-browser page, a map-config that
  never loads — is English.
- **Numbers and dates** go through `szFixed(x, d)`, `szLocaleNum(x)`,
  `szCompactNum(n)` ("5,6 Mio."), `szMonthYear(y, m)` and `szDuration(min)`:
  `Intl` in the UI language, and in English exactly the old `toFixed` /
  `toLocaleString()` / month-name output. The arrival clock uses the UI
  language too ("14:05"). Units do not follow the language: the reader's
  choice or the device locale decides metric or imperial (`streetzim.units`,
  140-view-home-about.js).
- **Find chips** are translated by chip id (`szChipLabel`, `chip.food` …),
  whatever label the ZIM's manifest carries; in English the manifest's
  label shows as before. Inside a sentence English lower-cases it ("No food
  & drink in this map"), German keeps the noun ("Keine Treffer für „Essen &
  Trinken“ in dieser Karte").
- **Place types** (`fast_food`, `museum`, Overture's `italian_restaurant`)
  go through `szPlaceType`: the table's `type.<key>` when it has one
  (~270 common types in German; inlined as one `type` object), else the key with spaces, as English
  always showed it. `type.*` keys are the one family no call site names;
  the tests accept any of them in a table.
- **State is never read back from text.** "Current location" as a routing
  end is the token `SZ_HERE` plus a flag on the input; "My location" on the
  Find page is `data-sz-here`; the smoke gates read `data-*` attributes and
  chip ids (B0 of the design).

| file | what |
|---|---|
| `resources/viewer/i18n/runtime.js` | `szT`, `szTn`, `szUseLanguage`, `szApplyI18n`, formatters, chip and type labels (ES5) |
| `resources/viewer/i18n/en.json` | every key and its English, collected from the code (generated; for translators and the build side) |
| `resources/viewer/i18n/de.json` | German |
| `tools/build_i18n.py` | collects en.json, inlines runtime + tables; `tools/build_viewer.py` runs it |
| `tests/test_viewer_i18n.py` | tables complete with matching placeholders and plural forms; no visible markup text or English literal in a text sink outside szT |
| `tests/viewer_i18n_js.test.mjs` | the runtime, and the tables each built page carries |
| `tools/i18n_pseudo_check.mjs` | browser check (CI): pseudo-locale and German on a real ZIM |

## Changing a string

1. Write it as `szT('area.what', 'English text', vars)` (or a `data-i18n*`
   attribute). The English must be a literal: the collector reads it.
2. `python tools/build_viewer.py`, then `bash scripts/sync-drive-viewer.sh`.
3. Add the translation to `resources/viewer/i18n/de.json`. The tests fail
   on a missing or stale key and on placeholders that differ from the
   English.

German style: formal "Sie" in full sentences (explanations, error
advice), the infinitive in short prompts and hints ("Start eingeben",
"Mindestens 2 Zeichen eingeben", "für mehr hineinzoomen"); standard
spelling with ß; terms that read right in Germany, Austria and
Switzerland (a first-level region is "Region", not "Bundesland").
Check a new string at 320 px: German runs ~40% longer, and buttons in
the navigation HUD and the Find page header have no room to spare.

Changing an English text under the same key leaves the German describing
the old one: give the string a new key when its meaning changes.

## Known limits of the checks

The lint in `tests/test_viewer_i18n.py` is best effort. It sees English
that goes straight into a text sink (`textContent`, `innerHTML`, `title`,
`placeholder`, `value`, plain or `+=`; `createTextNode`, `setAttribute`
of aria-label/title/placeholder/alt, the viewer's own status and toast
helpers), or that sits in a variable or table used directly in one. It
does not follow text through function arguments, object properties set
elsewhere, string building across statements, or a helper it does not
know. The browser pseudo-locale check (`tools/i18n_pseudo_check.mjs`) is
the backstop, and it only sees the states it visits: a failure state the
test map cannot produce is skipped with the reason, and in rows that join
a label with data ("[restaurant] · Ville Haute") a part without any
bracket is taken as data, so an untranslated word there passes.

## Pseudo-locale and the URL override

`?uilang=qps` shows every translated string as `[text]`: anything on screen
without brackets that is not data was missed. `?uilang=de` shows a map in
German whatever its `language` — for checking the translation on an English
or French test ZIM. Neither is remembered. The smoke gates take
`SMOKE_UILANG=qps` (or `de`) to run the same checks on a translated viewer.

## Adding a language

Copy `de.json` to `<code>.json` (ISO 639-1, the code `--language` takes),
translate every value and keep every `{placeholder}`. Counts need the
language's plural categories (`Intl.PluralRules`: one/other for German,
one/few/many/other for Polish); add the language to `PLURAL_FORMS` in
`tests/test_viewer_i18n.py`. Rebuild; each page grows by about the size of
its table (German: ~20 KB in index.html, ~11 KB in places.html).
