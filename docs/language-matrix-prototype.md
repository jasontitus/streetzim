# Language matrix prototype: interfaces

Status: prototype spec, 2026-10-13, for the plan of record in `docs/language-matrix.md`. The regions are California and Greece. The workstreams share these interfaces:
- pack builder
- viewer
- PWA reader
- merger and recipes
- builder page

## Bases

A base is a region's published default ZIM, built with the normal builder and these settings:
- **Tiles:** multilingual, carrying `name:xx` for ar de el es fa fr he hi id it ja ko nl pl pt ru th tr uk vi zh. They are made by regional tilemaker runs and passed with `--mbtiles`.
- **Language and Wikipedia:** `--language` is the region's own language: California `en`, Greece `el`. Wikipedia comes from the matching local Kiwix ZIM in `/storage/streetzim/wiki-src`.
- **Kiwix search:** Kiwix place pages and Xapian (libzim writer, `--zim-builder python`). That gives a raw, front-only `X/listing/titleOrdered/v1`. Gate: its count ≥ the place pages.
- **Paths:** no path at or after `~`; the builder never writes one.

The base's own Wikipedia stays where it is today: `wiki-article/<Title>`, `wiki-geo-index.json`, `wiki-image/…`.

## Wikipedia packs

A pack is a ZIM, `osm_<region>_wiki-<xx>_<date>.zim`, whose content paths all live under `~w/<xx>/`:

| path | what |
|---|---|
| `~w/<xx>/wiki-article/<Title>` | a cleaned article (the builder's `clean_article_html`), front article, title = the article title |
| `~w/<xx>/wiki-image/<hash>.webp` | images, named as the base names them (content hash) |
| `~w/<xx>/wiki-geo-index.json` | `{title: [lat, lon, type, desc, qid]}`: the base format plus the Q-ID as the 5th element |
| `~w/<xx>/wikidata-text.json` | `{qid: [label, description]}` in xx for every region Q-ID with an xx label or description, not only those with an article. Popups use it. |
| `~w/<xx>/pack.json` | `{"lang": "xx", "region": "...", "base_uuid": "...", "articles": N, "images": N, "source": "wikipedia_xx_all_maxi_YYYY-MM.zim", "built": "YYYY-MM-DD"}` |

**Pack metadata (M/):** Name `osm_<region>_wiki-<xx>`; Title of at most 30 UTF-16 units; Language (ISO 639-3); Description of at most 80 characters; Date; Creator, Publisher; Illustration 48×48 (copied from the base). No Xapian. Its own v1 listing lists the articles as front articles. In the prototype, Kiwix's own search (the base's Xapian title index) finds base pages only. Pack articles are reached from the map's Wiki panel and place popups.

**Contents and links:**
- **Which articles:** articles about the region's places, i.e. the base's Q-IDs (`wikidata/` chunks, and search records' `q`), that have a sitelink in xx Wikipedia. Sitelinks come from the local xx Wikipedia ZIM. Its `wikidata`/`page_props` metadata are not exposed, so the pack builder resolves Q-ID → title. The robust offline route is the language's `page_props` dump (wikibase_item → page_id) together with its `page` dump (page_id → title), from dumps.wikimedia.org. The other route is polite Wikidata sitelink batches. Either way the result is cached.
- **Back-to-map bar:** the article's bar links `../../../index.html#…`. A pack article sits 3 levels deeper than `wiki-article/` does in the base.
- **Links between articles:** links to other articles in the same pack stay relative (`./Other_Title`). A link to an article not in the pack becomes plain text, as the builder does today.

## map-config.json (the merged file's, generated by the recipe)

The base's `map-config.json`, plus:
```json
"wikiPacks": [{"lang": "th", "prefix": "~w/th/", "articles": 512}, ...],
"language": "<map/UI language chosen>",
"baseLanguage": "<the base's own language: its map-config's language, else en>"
```
The base's own Wikipedia stays implicit (`hasWikiArticles`, `wiki-article/`). `language` replaces the base's, so the merge keeps the base's as `baseLanguage`: the viewer needs it for the bilingual labels and to name the base's Wikipedia. Without it the viewer takes the map language as the base's when no pack is in the map language, and otherwise draws one-language labels as today and calls the base's Wikipedia just "Wikipedia". The recipe overrides `map-config.json`, an entry the base already has, with these generated bytes.

## Viewer (in-ZIM and PWA)

- **Several geo-indexes.** Read `config.wikiPacks`. Load each pack's `wiki-geo-index.json` next to the base's. Join them by Q-ID, from the 5th element in packs and from search records' `q` in the base.
- **Which article opens.** The Wiki panel and place popups offer the map language's article first, then the base's language, then the other packs. A place with articles in several languages shows "Also in: …" links.
- **Links:** article links point to `<prefix>wiki-article/<Title>`.
- **Bilingual labels.** When the map language differs from the local language, labels show the local name, then a second, smaller line with `name:<lang>` where it exists and differs (a MapLibre `format` expression). Otherwise the labels are exactly as today.
- **Popups and place sheet:** they show `wikidata-text.json`'s label and description in the map language when present.
- **Old base, no packs:** with no `wikiPacks` the viewer behaves exactly as today.
- **Bilingual labels, in detail.** "Local" is the base's own label rule (`baseLanguage`); point labels (places, POIs, water, peaks, parks, airports) get the second line, road labels along lines stay one line. Popup titles and the Wiki list show "local · visitor's name"; searches still look places up by the local name. Otherwise the style is byte for byte today's.
- **Geo-index order.** The base writes `[lat, lon, type, qid, desc]`; a pack, per this spec, `[lat, lon, type, desc, qid]`. Each is read in its own slots; only a pack whose Q-ID slot holds no Q-ID is read the base's way round. A Q-ID two titles carry maps to the later title, in packs as in the base.
- **Language codes** in `wikiPacks`, `language` and `baseLanguage` are compared in lower case, and a map in `zh-Hans` takes the `zh` Wikipedia first. A pack's prefix must be `~w/<its lang>/`.
- **`sw.js`:** `isArticle` also matches `~w/<xx>/wiki-article/`, so the back-to-map bar is injected for older articles too.

## PWA reader (web/drive/zim-reader.js)

Decode a zstd cluster as a stream up to the end of its frame. Do not decode up to the next known cluster boundary. In a merged file, the base's last cluster is followed by its old tables, not by another cluster.

## Recipes (`streetzim-recipe/2`)

There is one per menu entry (region, map language L, packs = the region's own ∪ {L} ∪ {en}, minus the base's own language):
```json
{"format": "streetzim-recipe/2", "uuid": "...", "name": "osm_<L>_<region>", "size": N, "md5": "...",
 "base": {"file": "osm-<region>-<date>.zim", "size": N, "range": [cluster_start, dirents_end],
          "chunk": 16777216, "sha256": ["...per 16 MiB chunk of the base file, from offset 0..."]},
 "packs": {"th": {"url": "<proxy>/<item>/<file>", "size": N, "chunk": 16777216, "sha256": [...]}},
 "segments": [{"src": "inline", "len": n, "data": "<base64>", "sha256": "..."},
              {"src": "base", "off": a, "len": n},
              {"src": "pack", "pack": "th", "off": a, "len": n},
              {"src": "md5"}]}
```

**How the browser uses a recipe:**
- It reads base ranges from the visitor's local file and pack ranges through the range proxy (packs are `*.zim` in `streetzim-*` items, as the proxy requires).
- It checks every base and pack chunk it touches against the SHA-256 lists, and every inline segment against its own SHA-256.
- It writes the segments in order, computing the MD5 as it goes.
- Then it compares the MD5 with the recipe's. That MD5 comes from the gated merge on the build host for that menu entry, or, for unsampled entries, from the planner run that wrote the recipe, which computes it exactly.

**Where things live:** recipes are published on the site at `/lab/build/recipes/<region>/<L>.json`. Packs go in the archive.org item `streetzim-<region>-lang`.

## Required showcase entries

The prototype passes only if these four menu entries pass every gate: California → de, California → th, Greece → de, Greece → th. That is a German and a Thai visitor to each region.
- The German UI table exists; Thai's is added, machine-translated and marked as such.
- Greece's entries carry the Greek pack as the region's own language.

## Gates (build host, per region per round)

For the base:
- zimcheck
- the v1 count

For each pack:
- zimcheck
- metadata limits

For each menu entry (all, or a sample):
- merge
- `verify_merge`
- zimcheck `-A`
- kiwix-serve `/suggest` and an article fetch
- the PWA opening the merged file
- `kiwix_viewer_gate.sh`

## Builder page (/lab/build/, outside /drive/)

- **Inputs:** pick a region and map language; choose the local base file; the page shows which packs the menu adds, with their sizes.
- **Output:** "Save as…" (File System Access), or a service-worker streamed download.
- **Analytics:** GA4 events `build_start`, `build_progress` (25/50/75%), `build_end` (also on pagehide) and `build_probe`.

  Parameters: region, lang, packs, mb, sink, ttfb_ms, mbps_avg, mbps_p10, retries, resets, hidden_s, outcome, hash_ok.

  Nothing is sent when `navigator.webdriver` is set, on localhost, with `?notrack`, or with `localStorage.sz_dev`.
