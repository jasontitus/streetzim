## Update 2026-09-19 ~04:00 CEST — safe-area regression and six UI overlaps

A user screenshot from **Kiwix on iOS** showed the on-map search overlay ~120 px
down the map. Two distinct bugs, both now fixed and shipped in
`osm-switzerland-2026-09-19c.zim` (verified listed on archive.org).

**1. Safe-area insets are NOT zero in Kiwix (`49672cc`).** The mobile merge
(`b861cc4`) added `--top-inset: env(safe-area-inset-top)` with a comment
asserting it is "0 in a browser tab and inside Kiwix". It is not: Kiwix's
WKWebView reports a non-zero inset although the WebView already sits below the
app chrome, so it double-counted and everything top-anchored slid down. Now
defaults to 0 and lifts only under `(display-mode: standalone)` or the
`.sz-standalone` class from `navigator.standalone`. Three JS-inlined toast
styles and the build stamp called `env()` directly and bypassed the variable —
routed through `var(--top-inset)`.

**2. Six UI overlaps (`a8a2f9d`).** Fixing (1) pulled the search bar into
MapLibre's zoom column. `tmp/overlap-check.mjs` (load via kiwix-serve, report
every pairwise overlap at 320/390/430) found six, not one:

| fix | change |
|---|---|
| `#search-container` | `max-width` `calc(100% - 100px)` → `calc(100% - 128px)` |
| `#controls` | `top` 120px → 152px |
| `#attr-btn` | `bottom` 36px → 58px |
| `#info` | `bottom` 36px → 84px |
| scale bar (`.maplibregl-ctrl-bottom-left`) | `bottom` 0 → 48px |

Only the first three were caused by the inset fix. `#info`/`#attr-btn` were
`bottom:36px` before the merge and the scale bar was always at 0; MapLibre's
attribution wraps to a 44 px band (y=790..834) on a phone and they all sat
inside it. The Kiwix inset had been cushioning them.

**`tmp/ship-layout-fixed.sh`** runs the overlap check as a HARD GATE before any
upload. Run 1 exited `LAYOUT STILL BROKEN` and shipped nothing; run 2 reported
`NO OVERLAPS` at all three widths, passed six gates, shipped.

### Two traps found while checking it

1. **`rc=6` is success, not failure.** `upload_validated.sh` returns 6 for
   "transferred, listing pending". `build-refresh-queue.sh` logs that as
   `UPLOAD FAILED` and writes `upload-failed` to `queue-refresh.tsv`. The
   australia-nz file is on archive.org byte-exact (8,274,084,040 remote ==
   local, delta 0). Do NOT re-upload on the strength of that label — check the
   item metadata first.
2. **The build log's viewer `sha1` cannot detect our edits.**
   `log_viewer_freshness()` hashes only the **first 512 bytes**, so the
   regressed (444,949 B) and fully-fixed (447,380 B) viewers both print
   `sha1=3fad4900673a`. **Size is the discriminator.** Anything relying on that
   sha to prove viewer freshness is reading a constant.
