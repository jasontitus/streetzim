# build-proxy — the /build/ page's worker and the language torrents' webseed

A language version of a map (the file https://streetzim.web.app/build/
assembles in the browser) is stored nowhere: it is the base map and its
Wikipedia packs on archive.org plus a few MB of generated bytes. This worker
serves it anyway, as one ordinary file with HTTP ranges, so that

- each language version can have a **torrent** whose webseed (BEP 19) is
  this worker: a torrent client downloads it with no peer online, and every
  visitor who built the same file in the browser (byte for byte the same,
  same infohash) can seed it;
- the same URL is a **plain download** of the language version.

Nothing runs on the build host and nothing is stored here: the bytes come
from archive.org (one ranged GET per part, piped through) and from small
blobs published with the recipes on the site.

```
GET /merged/<region>/<lang>/<recipe uuid>/<file>.zim      Range: bytes=a-b
GET /<archive.org item>/<file>.zim                        (the preview proxy's handler)
```

Files:

- `merged-webseed.js` — the handler. It reads the language version's segment
  index, `/build/recipes/<region>/<lang>.ws.json` on the site (written by
  `tools/langpack/lang_torrents.py`, a few KB: parts that are byte ranges of
  archive.org files or of `ws-<sha256>.bin` blobs), and streams the requested
  range. The recipe UUID is in the URL: once a map or its packs change, the
  old torrent's URL answers 404 ("out of date") instead of other bytes —
  after asking the site itself, past any cache, for the current index.
- `worker.js`, `wrangler.toml` — Cloudflare Workers packaging
  (`streetzim-build-proxy`, separate from `streetzim-preview-proxy` so each
  can be switched off alone), the switches and the daily meter.
- `serve-local.mjs` — the same on Node, on 127.0.0.1, for tests
  (`tools/langpack/webseed_e2e.py`, `tests/build_proxy_merged_js.test.mjs`).

## Limits and budget

Cloudflare's free plan (developers.cloudflare.com/workers/platform/limits/):

- **100,000 requests a day per account**, not per worker: this worker and
  `streetzim-preview-proxy` (the /build/ page's downloads and the /drive/
  preview) share them. Every request counts, including a 503 from a switch
  or the meter. Only `workers_dev = false` with no route (or deleting the
  worker) stops the counting.
- **The daily meter**: `WEBSEED_DAILY_BUDGET` (default 50,000; 0 switches
  the webseed off) caps `/merged/` requests per UTC day, so torrents cannot
  use up the preview's share. The `METER` Durable Object (as in
  `wrangler.toml`; SQLite-backed Durable Objects are on the free plan) keeps
  one count for all isolates: each isolate asks it before its first answer,
  then reports every 25 requests and, through `ctx.waitUntil`, 20 s after its
  first unreported one (so a quiet isolate's last few are counted too). The
  stub is made inside each report (workerd refuses I/O through an object
  made by another request). While the meter cannot be reached the webseed
  answers 503 (fail closed: better that than the shared 100,000 used up).
  Without the binding each isolate counts on its own. Over the budget
  `/merged/` answers 503 at once (still a request) until 00:00 UTC; peers and
  the /build/ page keep working. Limits of the count: each active isolate can
  run up to about 25 requests (or 20 s of requests) past the budget before
  its report lands, so the real cap is the budget plus ~25 per busy isolate;
  and when the meter fails, the webseed is refused for 5 s before it is
  asked again.
- **10 ms CPU per request** (waiting on fetch does not count): the handler's
  own work is about 0.5 ms; the archive.org bodies are piped into a
  FixedLengthStream.
- **50 subrequests per request**: `lang_torrents.py` keeps every 16 MiB
  window (libtorrent's largest web seed request) at 40 or fewer (index,
  blobs, archive.org parts), raising its threshold for short segments when it
  must; `site_check.py` checks it. A bigger range is cut to the longest
  prefix that fits (a 206 for fewer bytes; the client asks for the rest),
  and a whole-file GET that does not fit is refused with 416 (ranges only).

How many requests a download costs depends on the client:

| client | request size | a 1.2 GB language version |
|---|---|---|
| libtorrent (qBittorrent, Deluge, …) | up to 16 MiB (`urlseed_max_request_bytes`) | about 90 requests (measured: 4 per 51 MB) |
| a client asking one piece at a time | the piece length (1 MiB here) | about 1,100 requests |
| a browser or `curl` (the plain download) | the whole file | 1 request |
| the /drive/ viewer ("Preview in browser") | a 128 KiB block or one cluster | about 120 to open, then 55-75 a minute (docs/online-preview.md) |

So the 50,000 budget is roughly 45 per-piece downloads, 550 libtorrent
downloads or 100 five-minute previews a day, shared. Workers Paid
($5/month) removes the daily cap.

## Staleness and archive.org

The index records each archive.org file's size and, when ship_packs.sh had
its metadata, its ETag (`"<mtime hex>-<size hex>"`). The worker sends
`If-Range: <ETag>` and takes only a 206 for exactly the asked bytes of a
file of that size. A file replaced since (a re-upload) answers 200 or
another size: the version is out of date. The worker opens the range's
first archive.org part before it sends any header, so it answers 404 "out
of date" (a torrent client drops the web seed after one such answer)
instead of a 206 cut short (which libtorrent retries about once a second),
and the isolate remembers the version as out of date. The index is kept by
an isolate for at most 5 minutes; a UUID it does not know is checked with
the site itself, past every cache, before a 404.

A base whose recipes are published is frozen against in-place viewer
patches (user decision 2026-10-21): `ops/cloud/upload_validated.sh` refuses
(exit 7) to re-upload such a base with other bytes, and
`ops/cloud/rollout_viewer_patch.sh` skips it (row `frozen-published`),
unless `LANGPACK_RESHIP_AFTER_PATCH=1`; then upload_validated.sh queues the
region in `langpack-reship.tsv`, and `ops/langpack/reship_queue.sh` (run
after the rollout: ship_packs.sh can take hours per region, which inline
would stall the rollout) regenerates the recipes, the torrents and their
indexes (new UUIDs, the new ETag). Only a positive match blocks: an
unreadable recipes folder or region.json, or a base without an md5, is not a
match, and a checker that fails is a warning (the upload goes on; the
rollout skips the region unpatched, row `freeze-check-failed`). The check
runs only when bytes would be sent, so a finisher for a file archive.org
already lists completes. Callers log exit 7 as "frozen: published base".
An archive.org answer with the same ETag and size that ignores the Range
(transient) is tried again and then answered 503 with Retry-After; only
another ETag or size marks a version out of date, which an isolate
remembers for 10 minutes.

## Deploy from your laptop

You need Node.js 22 or later (current wrangler 4 requires it), git, and a
login to the Cloudflare account that already runs `streetzim-preview-proxy`
(the two share that account's free-plan requests; see Limits).

```sh
git clone https://github.com/jasontitus/streetzim.git && cd streetzim && git checkout lang-torrents && cd build-proxy
npx wrangler@4 login      # opens the browser
npx wrangler@4 deploy     # production: SITE_ORIGIN https://streetzim.web.app, from wrangler.toml
```

For a site on a Firebase preview channel (the recipes, indexes and blobs
are published only there), give the worker that channel's origin:

```sh
npx wrangler@4 deploy --var SITE_ORIGIN:https://<preview channel origin>
```

A `--var` applies to that deploy only: a later plain `deploy` goes back to
wrangler.toml's values, so repeat it on every deploy for the channel.

`deploy` prints the upload, the bindings (`env.METER (WebseedMeter)`,
`SITE_ORIGIN`, `UPSTREAM`, `WEBSEED_DAILY_BUDGET`), and the worker's URL,
`https://streetzim-build-proxy.<account>.workers.dev` (the preview proxy's
workers.dev subdomain), with a version ID. The first deploy also applies
the meter's Durable Object migration (`v1`).

Check it with a published region (the webseed URL of each language is in
its index on the site):

```sh
SITE=https://streetzim.web.app            # or the preview channel's origin
WS=$(curl -s "$SITE/build/recipes/<region>/de.ws.json" | python3 -c 'import json,sys; print(json.load(sys.stdin)["webseed"])')
curl -sI "$WS"                     # 200, Accept-Ranges: bytes, Content-Length = the language version's size
curl -s -r 0-99 "$WS" | wc -c      # 100
python3 ../tools/langpack/webseed_smoke.py --site "$SITE" --region <region> \
    --webseed https://streetzim-build-proxy.<account>.workers.dev
```

webseed_smoke.py (Python 3, standard library only) checks every language
of the region: HEAD, the first, last and spread pieces, and a range across
every part boundary, each against the torrent's piece hashes. It prints a
JSON line per language and exits 0 when all pass.

Kill switches (a redeploy each, live within seconds; for a preview channel
add its `--var SITE_ORIGIN:…` too):

```sh
npx wrangler@4 deploy --var MERGED:0                     # webseed and direct downloads off
npx wrangler@4 deploy --var OFF:1                        # everything off (503)
npx wrangler@4 deploy --var WEBSEED_DAILY_BUDGET:10000   # a lower daily cap
```

Switched-off requests still count against the account's 100,000 a day.
To stop that, remove the worker:

```sh
npx wrangler@4 delete     # asks first; removes the worker and its meter
```

Torrents keep working wherever peers seed them, and clients drop a webseed
that stops answering. The webseed origin is written into each torrent, so
moving the worker to another origin means running `lang_torrents.py` again.
That gives new torrent files with the same infohash, because the infohash
covers only the file.

### On the build host, after the deploy

`LANGPACK_WEBSEED=https://streetzim-build-proxy.<account>.workers.dev` in
`ops/langpack/host-env.sh`, or in the ship run's environment. With it,
`ops/langpack/ship_packs.sh` writes a torrent per language entry beside the
recipes (`<L>.torrent`, `<L>.ws.json`, `ws-*.bin`). site_check.py checks
them: every piece, the webseed origin, the ETags and the subrequest bound.
They are then sealed and published with the recipes
(`ops/langpack/publish_site.sh`, then the site deploy). If only the torrent
files fail the check, ship_packs.sh strips them and publishes the recipes
without. The page shows a "Torrent" link per language. Optionally,
`web/build/build-config.js` can send the /build/ page's own range requests
through this worker instead of the preview proxy:
`window.STREETZIM_BUILD_PROXY = 'https://streetzim-build-proxy.<account>.workers.dev'`.

## Local test under workerd (no Cloudflare login)

`wrangler dev --local` runs the worker in workerd, the Workers runtime, with
the METER Durable Object. That exercises what Node cannot:
FixedLengthStream, the blob copies, HEAD's Content-Length and the meter.
Start the stand-ins and point the worker at them. wrangler writes
`.wrangler/` next to wrangler.toml, so on the build host use a clone outside
the production checkout.

```sh
cd build-proxy
npx wrangler@4 dev --local --ip 127.0.0.1 --port 8799 --persist-to "$TMPDIR/meter" \
  --var SITE_ORIGIN:http://127.0.0.1:<stand-in> --var UPSTREAM:http://127.0.0.1:<stand-in>/download/
python3 ../tools/langpack/webseed_smoke.py --site http://127.0.0.1:<stand-in> --region <region> --via http://127.0.0.1:8799
```

`tools/langpack/webseed_e2e.py`'s `ranged_server` is the stand-in for both
archive.org and the site. Checked 2026-10-22 on Greece:

- every piece of two torrents and their MD5s;
- a libtorrent webseed-only download;
- the meter with WEBSEED_DAILY_BUDGET=5: 5 answers, then 503s. A restart
  with the same `--persist-to` keeps the count, the 20 s tail report
  included.

Through a fault-injecting proxy in front of the archive.org stand-in:

- archive.org 500s, and a 200 with the same ETag, answer 503 with
  Retry-After and leave the version usable;
- another ETag answers 404 "out of date", and that version (not the other
  languages) stays out of date until the 10 minutes are up.
